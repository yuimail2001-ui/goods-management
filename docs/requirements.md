### 3.1での主な変更と、その理由

#### イベント管理（F006〜F009）をスコープ外とする

当初は、ツアーとイベントを別テーブルで管理し、グッズを「ツアーまたはイベントのどちらか一方」に紐づける設計としていた。実装を進める中で、以下の理由からツアー管理に一本化した。

- グッズの親が2種類あると、`tour_id` と `event_id` のどちらか一方のみを許す制約が必要になり、初期版としては複雑になる
- 管理したい対象（ライブツアー、ファンミーティング、ドラマ関連イベント等）は、いずれも「名前と開催期間を持つ催し」として `tours` テーブルで表現できる
- まず1種類で動くものを完成させ、必要になった時点でイベントを追加するほうが、学習の段階として適切と判断した

#### カードIDを自動採番に変更

当初はカードIDを手入力（`M001` 形式）とする想定だったが、重複登録を防ぐため、ツアーIDと連番による自動生成（`T1-001` 形式）に変更した。これにより、要件「同じ分類内でカードIDが重複しないようにする」をアプリ側で保証できる。

#### 検索機能とコンプリート率表示を次フェーズへ繰り延べ

F012（グッズ検索）、F020（カードID検索）、F022（コンプリート率表示）は未実装とした。まずCRUDと画像アップロードを完成させることを優先した。

# 3. システム概要

## 3.1 システムの目的

ライブツアーやイベントごとにグッズを登録し、購入状況や所持状況を管理する。

また、トレーディングカードを専用画面で管理し、カード番号ごとの所持状況やコンプリート率を確認できるようにする。

## 3.2 対象範囲

初期バージョンでは、**1アーティストのみ**を管理対象とする。

### 管理対象

- ライブツアー
- イベント
- グッズ
- トレーディングカード
- カードの所持状況

### 初期対象外

- 複数アーティストの管理
- SNS機能
- ユーザー間の交換機能
- 決済機能
- ECサイトとしての販売機能
- 複雑な画像加工機能

## 5.3 トレーディングカード管理

トレーディングカードは、グッズ管理とは別の専用画面で管理する。

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| F018 | トレカ登録 | カードID・メンバー名・所持状況を登録する | 必須 |
| F019 | トレカ一覧 | カードを一覧表示する | 必須 |
| F020 | カードID検索 | カードIDや番号で検索する | 必須 |
| F021 | 所持状況変更 | 未所持・所持を変更する | 必須 |
| F022 | コンプリート率表示 | 所持数と全カード数から割合を表示する | 高 |
| F023 | カテゴリ分類 | ツアー・イベントごとに分類する | 高 |
| F024 | トレカ編集 | 登録済みカードを編集する | 必須 |
| F025 | トレカ削除 | カード情報を削除する | 必須 |

### カードID

カードIDは、アルファベットと数字を組み合わせた形式とする。

例：

```text
M001
M002
M003
S001
S002
```

### 所持状況

- 未所持
- 所持

### コンプリート率

```text
コンプリート率 ＝ 所持カード数 ÷ 全カード数 × 100
```

### 要件に記載がないが実装した項目

| 項目 | 内容 |
|---|---|
| 画像アップロード | グッズ・トレカともに画像を1枚登録できる（5MBまで）。差し替え時は古いファイルを削除する |
| 所持枚数の管理 | 要件では「所持 / 未所持」の2値だったが、同じカードを複数枚持つ場合に対応するため `owned_count` を追加した |
| 論理削除 | 誤操作による消失を避けるため、全テーブルで `SoftDeletes` を採用した |

# 9. 非機能要件

## 9.1 操作性

- PC・スマートフォンの両方で利用できる
- レスポンシブデザインに対応する
- 登録・更新・削除の操作結果を画面に表示する
- API通信中はローディング状態を表示する
- エラー発生時はユーザーが理解しやすいメッセージを表示する

## 9.2 セキュリティ

- Laravelのバリデーションを利用する
- SQLインジェクション対策としてEloquentやパラメータ化クエリを使用する
- Vue.jsのテンプレートによる自動エスケープを活用する
- ユーザー入力値を適切に検証する
- `.env`などの機密情報をGitHubに公開しない

## 9.3 保守性

- コンポーネントごとに責務を分離する
- API通信処理をサービス層に分離する
- Controllerに複雑な処理を集中させない
- 命名規則を統一する
- READMEにセットアップ方法を記載する
